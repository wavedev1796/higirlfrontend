# HG-F3-031 - Blueprint de Render para el frontend

## Resumen

Se agrega `render.yaml` para desplegar el frontend en Render como Web Service,
en lugar de Vercel.

## Objetivo

Alojar el frontend sin depender de una cuenta en Vercel, que quedó bloqueada por
la verificación telefónica del registro.

## Por qué Render y no Railway

Railway se evaluó como alternativa y se descartó con datos de su propia página
de precios:

| | Railway | Render (gratuito) |
|---|---|---|
| Gratis real | $5 de crédito por 30 días; después **$1/mes** de consumo | Sin caducidad |
| Verificación | Tarjeta o cuenta de GitHub con antigüedad | Ya resuelta para el backend |
| Base de datos | Consume del mismo crédito | Postgres gratuito aparte |

$1/mes de crédito no sostiene un servicio activo, así que Railway habría dejado
de ser gratuito al mes exacto — justo antes de que sirva de algo. Y su
verificación es el mismo tipo de muro que bloqueó Vercel.

Render ya era necesario para el backend, así que el frontend no agrega ninguna
cuenta nueva.

## Web Service, no Static Site

Un Static Site en Render sale más barato en todo sentido: no consume horas de
instancia y no se suspende por inactividad. **No es viable aquí.**

`next build` marca dos rutas como dinámicas (`ƒ`, renderizadas bajo demanda):

```text
ƒ /chats            → lee searchParams.participante
ƒ /verificar-email  → lee el token del enlace del correo
```

Y `/afinidad/[id]` recibe ids de usuaria que solo existen en tiempo de
ejecución, sin `generateStaticParams`. Con `output: 'export'` la compilación
falla. Convertirlo a estático significa reescribir esas tres rutas: es un
cambio de producto, no de despliegue.

## Alcance Implementado

- `render.yaml` con un Web Service en el plan gratuito, región `oregon` (la
  misma que el backend), rama `feature/edu-2026-dev`.
- `startCommand` con `-H 0.0.0.0 -p $PORT` explícitos, por la misma razón que
  el backend (TICKET-024): dentro de un contenedor, un socket atado al loopback
  no es alcanzable desde fuera.
- `NEXT_PUBLIC_API_URL` como `sync: false`.

`NEXT_PUBLIC_API_ORIGIN` no se declara: `infrastructure/config/env.ts` la deduce
quitándole el sufijo `/api/v1` a la anterior.

## Pruebas Realizadas

```powershell
npm.cmd run build
```

Resultado: build correcto. La salida confirma además que existen rutas
dinámicas, que es lo que descarta el Static Site.

**No verificado:** el despliegue en sí. La sintaxis del Blueprint se contrastó
con la especificación oficial de Render, pero la comprobación real es el primer
despliegue.

## Advertencias

- **`NEXT_PUBLIC_API_URL` se incrusta durante `next build`, no se lee al
  arrancar.** Si cambia la URL del backend hay que **volver a desplegar**;
  editarla en el panel no basta.
- **750 horas de instancia al mes por cuenta, compartidas entre los servicios
  gratuitos.** Dos servicios encendidos todo el mes darían 1440 h y Render los
  suspendería. Como ambos se apagan tras 15 min sin tráfico, el consumo real es
  bajo, pero conviene no dejarlos despiertos.
- Frontend y backend se suspenden por inactividad: **la primera visita tras un
  rato tarda alrededor de un minuto**. Conviene despertar los dos antes de una
  demostración.
