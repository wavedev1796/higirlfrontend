# HG-F3-030 - Cierre de la auditoría ponytail del frontend

## Resumen

Se abordan los siete hallazgos restantes de
`docs/ponytail/2026-08-05-higirlfrontend.md`, tras los dos primeros que resolvió
HG-F3-029: se unifican el avatar y la forma de usuaria, se elimina el re-export
del cliente HTTP, y se borra código y CSS sin uso.

## Objetivo

Dejar una sola implementación de cada cosa duplicada y ningún archivo que
prometa algo que nadie consume.

## Correcciones a la auditoría

Al implementar aparecieron dos errores del reporte original, que conviene dejar
registrados:

| Hallazgo del reporte | Realidad |
|----------------------|----------|
| `UserRole` sin usos → borrar | **Falso.** Lo usa `User` en su mismo archivo; el grep de la auditoría excluía ese archivo. Se conserva. |
| "5 clases de Tailwind" (HG-F3-029) | Eran 5, pero el reporte decía 3: se contaron las del `<body>` y no las del `<html>`. |

El resto se confirmó.

## Alcance Implementado

### 1. `infrastructure/api/client.ts` eliminado

Era un re-export puro de `@/lib/api`. Convivían dos rutas de import para el
mismo cliente: 16 archivos usaban `@/lib/api` y solo 2 el wrapper. Esos dos
(`chat.service.ts`, `connections.service.ts`) pasan a importar directo. El alias
`fetchApi` que exponía no tenía consumidores.

### 2. `UserSummary` compartido

La forma `{ id, nombre, apellido, usuario, foto }` estaba declarada en cuatro
features. Ahora vive en `shared/types/user.types.ts` y los tipos de feature la
extienden:

```ts
export type ChatParticipant = UserSummary;
export type BlockedUser = UserSummary;
export interface ConnectionUser extends UserSummary { bio?, profesion? }
export interface MatchingUser extends UserSummary { ciudad?, bio?, intereses }
```

### 3. `Avatar` compartido

`ChatAvatar` y `ConnectionAvatar` eran el mismo componente —foto vía
`getProfilePhotoUrl`, iniciales como respaldo— con distinta clase CSS y tamaño.
Se reemplazan por `shared/components/ui/Avatar.tsx`, que recibe `person`,
`className` y `size`.

Las clases `chat-avatar` (52px) y `connection-avatar` (64px) **no cambian**: se
pasan por props, así que el CSS existente sigue aplicando igual.

`ProfileAvatar` queda fuera a propósito: pinta la foto como `background-image` y
admite previsualización de subida durante la carga. Es otro caso, no la misma
duplicación.

### 4. Borrados

- `shared/types/api.types.ts` completo (`ApiResponse`, `ApiErrorResponse`): cero usos.
- `shared/utils/cn.ts`: cero usos. La carpeta `utils/` queda vacía y se elimina.
- `shared/components/icons/`: carpeta vacía; los iconos vienen de `lucide-react`.
- 5 clases CSS sin referencia: `.connect-btn`, `.login-alert`, `.quick-link-item`,
  `.quick-links`, `.register-shell` (−74 líneas).

Sobre la última: `.register-shell` aparecía además dentro de un `@media`
compartiendo bloque con `.login-shell`, que **sí se usa**. Se quitó solo el
selector muerto, conservando la regla.

## Criterios de Aceptación

- [x] Una sola ruta de import para el cliente HTTP (`@/lib/api`).
- [x] Una sola declaración de la forma de usuaria (`UserSummary`).
- [x] Un solo componente de avatar para chat y conexiones.
- [x] Sin referencias a las 5 clases CSS eliminadas.
- [x] Llaves balanceadas en los 4 archivos CSS tras el borrado.
- [x] `UserRole` y `User` conservados (sí se usan).
- [x] Lint y build sin errores.

## Pruebas Realizadas

```powershell
npm.cmd run lint
npm.cmd run build
```

Resultado: ESLint sin advertencias, build de Next.js correcto.

Verificación en navegador sobre instancia limpia:

- `/register` renderiza; `.register-page` conserva `display: grid` y
  `place-items: center` tras eliminar la regla vecina `.register-shell`.
- `body` sigue en `flex` / `column` / `min-height: 100%` y `html` en `100%`.
- Sin errores de consola propios (solo CORS, esperado por correr en un puerto
  distinto al que autoriza el backend).

**No verificado visualmente:** el `Avatar` en una sesión iniciada (chat y
conexiones requieren login). Se apoya en el chequeo de tipos, en que el marcado
generado es idéntico al de los dos componentes anteriores y en que sus clases
CSS no se tocaron.

Nota: un dev server que llevaba rato corriendo mostraba `body { display: block }`
por CSS cacheado. En instancia nueva el estilo es el correcto; conviene
reiniciar el servidor de desarrollo tras estos cambios.
