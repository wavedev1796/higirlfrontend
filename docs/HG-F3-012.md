# HG-F3-012 - Solicitudes y conexiones

## Resumen

Se implemento en el frontend la gestion de solicitudes de conexion recibidas y
enviadas, las acciones para aceptar o rechazar solicitudes y la pantalla "Mis
conexiones". La implementacion consume el contrato existente del backend y
actualiza la interfaz inmediatamente despues de cada accion.

## Objetivo

Cubrir los criterios de aceptacion:

1. Pantalla de solicitudes recibidas y enviadas.
2. Acciones para aceptar o rechazar solicitudes recibidas.
3. Pantalla "Mis conexiones".
4. Reflejar cambios en tiempo casi real.

## Contrato backend verificado

```text
GET /api/v1/conexiones?estado=pendiente
GET /api/v1/conexiones?estado=aceptada
POST /api/v1/conexiones
PATCH /api/v1/conexiones/:id
```

Creacion:

```json
{
  "destinoId": 12
}
```

Respuesta a una solicitud:

```json
{
  "estado": "aceptada"
}
```

El valor tambien puede ser `"rechazada"`. El backend permite responder
unicamente a la usuaria destinataria y solo mientras la solicitud permanezca
en estado `"pendiente"`.

El listado devuelve conexiones donde la usuaria autenticada es origen o
destino. El frontend usa `origenId` y `destinoId` para separar recibidas y
enviadas y para identificar a la otra persona en "Mis conexiones".

## Implementacion

### Feature `connections`

Se creo el modulo:

```text
src/features/connections/
```

Incluye:

- Tipos alineados con la entidad `Conexion` del backend.
- Servicio para listar, enviar y responder solicitudes.
- Hook reutilizable con carga, errores y sincronizacion.
- Componentes para solicitudes, conexiones, avatar y navegacion interna.

### Rutas

```text
/solicitudes
/conexiones
```

`/solicitudes` ofrece controles segmentados para recibidas y enviadas.
`/conexiones` muestra las solicitudes aceptadas.

### Acciones

- Aceptar envia `PATCH /conexiones/:id` con estado `aceptada`.
- Rechazar envia `PATCH /conexiones/:id` con estado `rechazada`.
- Conectar desde Descubrir envia `POST /conexiones`.
- Los botones muestran estado ocupado y evitan solicitudes duplicadas desde la
  misma tarjeta.
- El resultado se comunica mediante una notificacion.

### Actualizacion casi en tiempo real

El backend actual no expone WebSocket ni Server-Sent Events para conexiones.
Por esa razon se implemento:

1. Actualizacion optimista al aceptar o rechazar.
2. Reconsulta inmediata despues de completar cada accion.
3. Reconsulta al recuperar el foco de la ventana.
4. Sondeo del listado cada 12 segundos.

Esto mantiene la respuesta de la interfaz inmediata y permite recibir cambios
realizados por otra usuaria sin recargar manualmente.

### Navegacion y responsive

Se agrego "Conexiones" a la navegacion principal y movil. El estado activo se
mantiene tanto en `/solicitudes` como en `/conexiones`.

Las filas usan una grilla estable para avatar, identidad y acciones. En
pantallas pequenas las acciones conservan dimensiones fijas y los textos largos
se truncan sin desplazar los controles.

## Ajuste posterior: paginacion de recomendaciones

Se verifico que el limite predeterminado de 5 pertenece al endpoint:

```text
GET /api/v1/matching/recomendaciones?page=1&limit=5
```

El endpoint de conexiones no expone actualmente parametros de paginacion.
Se agregaron controles anterior/siguiente al bloque Comunidad, usando los
campos `page` y `totalPages` retornados por matching. Cada pagina solicita y
muestra un maximo de cinco recomendaciones.

Tambien se agrego paginacion visible a la pantalla `/descubrir`, que consume:

```text
GET /api/v1/matching/descubrir?page=1&limit=5
```

Al cambiar de pagina se reemplazan los resultados actuales por los cinco
registros de la pagina solicitada. Los filtros reinician la consulta a la
primera pagina.
